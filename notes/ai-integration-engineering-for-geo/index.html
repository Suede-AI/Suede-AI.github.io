AI Integration Engineering for GEO: The Part of Your Product an Engine Can Cite Is the Part With a URL

By Jason Colapietro, Founder and CEO, Suede · Palm Beach County, Florida · November 16, 2026

When an AI assistant recommends a tool, it needs something to point at: a page it fetched, a description it can repeat, an address the person can open. A lot of AI products give it nothing. The useful part sits behind a login, inside a JavaScript bundle, or on a URL that changes every session. An engine cannot cite a page it cannot read, so it is more likely to name a competitor whose page it could.

Suede, the GEO and AI deployment studio Jason Colapietro founded in Palm Beach County, Florida, builds AI integrations with that problem in mind. The deployment side, keeping AI features stable in production, is covered in what shipping AI features across 17 live store apps taught Suede. This note is about integration: how to wire an AI feature into a product so the product itself becomes a source.

Why does the address matter so much?

Suede Sing is the clearest example Suede has. It had at most 5 users. After ChatGPT began naming it as a vocal coach and pitch trainer, it passed 1,000 active users, combined across all its platforms, within about a week. The full story is in the Suede Sing case study.

The vocal range test has a single public address, sing.suedeai.ai, that a person can open without an account. When an assistant names the tool, the person who asked can act on it in one tap. A tool that requires a download, a sign-up and an onboarding screen before it does anything gives the engine a weaker thing to recommend.

Suede now treats every AI feature's entry point as a permanent URL. It does not move between versions, it does not carry session tokens, and if it ever has to change, the old address redirects.

What should the page say before the AI runs?

A tool page often contains nothing but a button until a script loads and the model responds. A crawler that does not run the script, or does not wait for it, sees an empty page. Suede renders a plain description on the server: what the tool does, who it is for, what it does not do, and how the result is produced. The AI output then loads on top for the person using it.

That description is written the way the GEO paper by Aggarwal and colleagues found engines respond to: specific statements, sources where a claim needs one, and numbers only where they are real. In their KDD 2024 benchmark, adding citations, quotations and statistics raised visibility in generative answers by up to about 40 percent. For a tool page, the strongest version is short. Say what the tool measures and how, and cite the method if there is one.

Can AI crawlers actually reach it?

Test it directly. OpenAI documents separate crawlers for search (OAI-SearchBot), for training (GPTBot) and for fetches a user triggers (ChatGPT-User). Perplexity publishes its own list. A robots.txt rule copied from a template, or a firewall setting that challenges unfamiliar user agents, can block the search crawler while the site owner believes everything is open. Google's robots.txt introduction covers the syntax. Suede's view on which of these settings moved results and which were placebo is in crawler access: what mattered.

A product can allow the search crawlers and still block training crawlers. Those are separate decisions, and treating them as one is a common mistake.

How do you describe the product to machines?

With structured data that matches the visible page. Suede marks up app pages with SoftwareApplication (or MobileApplication for store apps), using the fields Google lists in its software app documentation, and links the app to its developer and its store listings. The goal is that an engine describing the product gets the name, category and maker right. Structured data for apps goes into the entity links in detail.

Should AI output become pages?

This is where integration engineering goes wrong most often. A model can turn every user query into a public page, and some teams do it to manufacture thousands of URLs. Google's spam policies name this directly as scaled content abuse, whether the pages come from a model or a person. Suede does not publish model output as indexable pages. The citable surface is the hand-written description of what the tool does. The generated output belongs to the person who asked for it.

The output still matters for GEO, in a different way. If a coaching tool invents a fact about someone's voice, that is the answer people screenshot and repeat. Jason Colapietro keeps AI outputs inside what the app can measure, so the explanation describes a result the app actually computed.

Questions people ask

Does an app need a web page at all if it lives in the stores? Suede thinks so. Store listings are good sources, but a page you control can carry structured data, a fuller description and a URL that works on any device.

Is fast loading part of this? Yes. The server-rendered description should arrive without waiting on the model, so both crawlers and people see the explanation immediately.
